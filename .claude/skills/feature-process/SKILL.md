# /feature-process — 기능마다 최종 코드까지 온 과정 채우기

대상: `$ARGUMENTS`

`format/02-tech-document.md` §3의 **「최종 코드까지 온 과정」**(깊게 쓴 기능 단위마다 처음 방식 → 부딪힌 문제 → 바꾼 방식 → 지금의 코드, 빠지면 **필수**)만 다루는 명령입니다.
빠진 기능을 찾고, 수강생에게 묻고, 답이 없을 때는 근거를 밝힌 **후보**를 추천합니다. 문서에 넣는 것은 수강생이 확인한 것뿐입니다.

## 지킬 원칙 (먼저 `CLAUDE.md`의 「반드시 지킬 원칙」을 다시 읽습니다)

- **겪은 일을 지어내지 않는다.** 추측은 추측으로만 다룹니다. 문서에 넣을 때는 수강생이 "실제로 그랬다"고 확인한 것만 **겪은 일**로 쓰고,
  확인하지 못한 추측은 **겪은 일처럼 쓰지 않습니다** — 그때는 §4-3의 "비교로 쓰기"(처음 떠올릴 법한 방식이었다면 어떤 문제가 생기는지를 지금 코드로 보이기)로만 넣습니다.
  면접에서 "그때 어떤 버그였나요?"라는 질문을 받았을 때 수강생이 답할 수 없는 문장은 넣지 않습니다.
- **수강생이 고른 것만 쓴다.** 추천은 대화창에 보여 주고, 기능마다 수강생이 고르거나 고친 뒤 "넣어 줘"라고 한 것만 프로젝트 문서에 씁니다(원칙 2). 한 번에 여러 기능을 쓰더라도 쓰기 전에 넣을 글 전체를 한 번 더 보여 줍니다.
- **커밋 기록은 사실, 해석은 추측.** 커밋 해시·날짜·바뀐 줄은 사실(✅)이고, "그래서 이런 버그였을 것"은 추측(⚠)입니다. 둘을 섞어 쓰지 않습니다.
- **남의 정보·비밀값을 옮기지 않는다.** 팀 프로젝트에서 남의 커밋은 해시·날짜·파일만 보고 메시지 원문을 문서에 옮기지 않습니다. 이름·이메일은 어디에도 쓰지 않습니다.
  비밀값이 들어 있을 수 있는 파일(`.env`, `*key*`, `*secret*`, `google-services.json` 등)은 열지 않습니다.
- 이 명령이 직접 `data/`를 고치지 않습니다. 문서에 넣은 것이 있으면 마지막에 `/portfolio-build <폴더>`를 자동으로 실행해 페이지에 반영합니다(§6).

## 0. 준비

1. 인자에서 프로젝트 폴더(`src/<폴더>/`)를 정합니다. 없으면 `src/`의 폴더 목록(이름이 `_`로 시작하는 것 제외)을 보여 주고 묻습니다.
2. 프로젝트 문서를 정합니다(`/portfolio-build` §1과 같은 규칙 — 폴더 바로 아래의 `.md` 하나, `_intake/`는 문서가 아님). 문서가 없으면 멈추고 `/portfolio-intake`·`/portfolio-check`를 안내합니다.
3. 읽을 기준: `format/02-tech-document.md` §3(「최종 코드까지 온 과정」)과 §4·§5의 문제 해결 사례 문단.
4. **코드 출처**를 이 순서로 찾습니다(먼저 찾은 것 하나).
   1. 인자로 받은 레포 주소·로컬 폴더 경로
   2. `src/<폴더>/_intake/intake.json`의 출처(`source`)
   3. 프로젝트 문서 머리 표·링크의 GitHub 주소
   4. 없으면 `src/<폴더>/code/`의 `.cs`만(커밋 기록 없음)
   찾은 출처는 §1의 결과와 함께 알리고, 틀렸으면 바로잡아 달라고 합니다. 레포 받기는 §3에서 필요할 때만 합니다.

## 1. 빠진 기능 찾기

프로젝트 문서를 끝까지 읽고 **깊게 쓴 기능 단위**(장·절을 따로 준 기능)를 모두 목록으로 만듭니다.

- 보지 않는 것: 표 한 줄로만 정리한 기능, 문서가 "팀원 작업"이라고 밝힌 절, 기능을 묶는 상위 제목(예: §3.1 아래에 §3.1.1~3.1.4가 있으면 하위 절만), 개요·시스템 구조 절.
- 다른 장(고민과 선택·AI 협업·결론의 문제 해결 사례 등)에 있어도 그 기능에 관한 과정이면 그 기능의 것으로 인정합니다. 그 기능 안의 문제 해결 사례(문제 → 원인 → 해결)가 있으면 충족입니다.
- **함정**: "바꾼 것"만 있고 그렇게 바꾼 이유가 된 문제가 없으면 없음입니다. 「지금 다시 보면」에 적은 문제를 고치지 않고 「다음 단계」로 미뤘다면, 그 문제는 실제로 바꾼 것의 이유가 아닙니다.
  비교 표만 있고 처음부터 그 방식을 골랐다면("왜 이 방법") 이 항목을 채우지 못합니다(그것은 4 · 고민과 선택).

대화창에 이 표를 보여 줍니다.

```markdown
| 절 | 기능 | 판정 | 근거 |
|---|---|---|---|
| §3.1 | 커브 기반 구르기 | 충족 | §3.1.1 — 고정 속도 → 미끄러짐 → 진행도 + 커브 |
| §3.3 | 미션 시스템 | 없음 | 지금 구조와 비교 표만 있음. 처음 방식·부딪힌 문제가 없음 |
```

빠진 기능이 없으면 "모든 기능에 과정이 있습니다"라고 알리고 끝냅니다.

## 2. 수강생에게 묻기 (한 메시지로 한 번)

빠진 기능마다 아래를 **번호 목록 하나로** 묻습니다. 기능이 많으면 기능마다 한 묶음씩, 한 메시지에 모읍니다.

> **§3.3 미션 시스템**
> 1. 이 기능을 만들면서 처음 짠 방식을 바꾼 적이 있나요? (버그·느림·고치기 불편함·기획 변경 무엇이든)
> 2. 있다면: 처음에는 어떻게 짰고, 무엇이 문제였고, 무엇으로 바꿨나요? 한두 줄이면 됩니다.
> 3. 없거나 기억나지 않으면 "모름"이라고만 적어 주세요. 코드와 커밋 기록을 보고 후보를 추천해 드리겠습니다.

- 문서·`_intake/`(재료집의 "버그 수정 후보" 표 등)에 이미 단서가 있으면 질문에 위치를 덧붙입니다("재료집 5절 커밋 표에 이 파일을 고친 커밋이 있습니다 — 이것이었나요?"). 내용을 옮겨 적지는 않습니다.
- 답을 기다립니다. 답이 오기 전에 §3·§4를 하지 않습니다.

## 3. 커밋 기록 보강 (코드 출처가 있을 때)

답이 "모름"·"없음"인 기능, 또는 답이 있어도 수강생이 "커밋으로 확인해 줘"라고 한 기능만 봅니다.

### 3-1. 받기
- GitHub 주소: `/portfolio-intake` §2-A와 같은 방법(로그인 창 없이 `git ls-remote`로 접근 확인 → 레포 밖 임시 폴더 `T="$(cygpath -u "$LOCALAPPDATA")/Temp/pfp/$(date +%H%M%S)"`에 `git clone --filter=blob:none --no-checkout`).
  비공개라 실패하면 로컬 폴더 경로를 달라고 하고, 토큰·비밀번호는 입력하지 않습니다. 오래 걸리면 `run_in_background`.
- 로컬 폴더: `.git`이 있으면 그 폴더를 읽기만 합니다(아무것도 쓰지 않음, checkout·reset 금지). `.git`이 없으면 "커밋 기록이 없어 코드만 보고 추천합니다"라고 알립니다.
- 셸은 Bash 도구(Git Bash), 매번 절대 경로, `git -C "<폴더>" …` 형식. 커밋 명령에는 `--no-renames`를 붙입니다.

### 3-2. 기능의 파일 찾기
문서 그 절의 코드 블록·글에 나온 클래스·메서드 이름으로 파일을 찾습니다:
`git -C "$T" ls-tree -r --name-only HEAD | grep -E '/(ClassName)\.cs$'` (여러 개면 문서의 다른 이름으로 좁히고, 그래도 여러 개면 수강생에게 묻기).

### 3-3. 그 파일의 기록 읽기
```bash
git -C "$T" log --no-renames --date=short --format='%h %ad %ae %s' -- '<경로>'
```
- 팀 프로젝트(문서에 [팀]이 있거나 인원 2명 이상)면 `git shortlog -sne --no-merges HEAD`를 **대화창에만** 보여 주고 본인 계정을 고르게 한 뒤, 본인 커밋만 메시지 원문을 봅니다. 남의 커밋은 해시·날짜만.
- 후보 커밋 고르기: 메시지에 `fix`·`bug`·`수정`·`버그`·`고침`·`오류`·`안 됨`·`refactor`·`리팩`·`변경`·`바꿈`이 있거나, 그 기능의 핵심 메서드를 크게 바꾼 커밋. 많으면 5개까지.
- 후보마다 바뀐 부분만 봅니다: `git -C "$T" show --no-renames --format='%h %ad %s' <해시> -- '<경로>'`(blob을 받아 오므로 5개 안팎으로 제한). 핵심 메서드의 예전 모양은 `git -C "$T" show <해시>^:'<경로>'`에서 그 메서드 부분만.
- 커밋이 아주 적은 레포(5개 미만이거나 `.cs` 대부분이 한 커밋)는 "한꺼번에 올린 레포라 과정 기록이 없습니다"라고 알리고 코드만으로 추천합니다.

여기서 얻는 것은 **사실**(✅ 해시·날짜·바뀐 줄)입니다. 무엇이 문제였는지는 아직 추측입니다.

## 4. 추천하기

기능마다 아래 셋 중 하나로 대화창에 보여 줍니다. 문장은 짧게, 문서의 말투(경어체·평서체)에 맞춥니다.

### 4-1. 수강생이 답한 경우
답을 처음 방식 → 부딪힌 문제 → 바꾼 방식 → 지금 코드(문서의 어느 코드 블록·줄인지) 순서로 **정리만** 합니다. 답에 없는 사실을 보태지 않습니다.
빠진 고리(예: 문제는 있는데 처음 방식이 없음)가 있으면 그 고리만 다시 묻습니다.

### 4-2. 커밋으로 뒷받침되는 추측
```markdown
(형식 예시 — 아래 이름·해시는 실제 프로젝트와 무관)
**§3.1.2 전기가오리** — 커밋으로 찾은 후보
- ✅ 사실: `a1b2c3d` (2026-08-21) `ElectricRay.cs`의 마비 해제가 `Invoke("Release", 3f)` → `UniTask.Delay(…, cancellationToken: destroyCancellationToken)`로 바뀜
- ⚠ 추측: 마비 중에 물고기가 사라지면 Invoke가 남아 오류가 났을 수 있습니다(지금 코드가 destroyCancellationToken을 쓰는 이유와 맞음)
- 넣는다면: 처음 방식(Invoke로 3초 뒤 해제) → 부딪힌 문제(⚠ 확인 필요) → 바꾼 방식(UniTask + 취소 토큰) → 지금 코드(§3.1.2 코드 블록)
- 확인할 것: 그때 실제로 오류가 났나요? 기억나면 무엇이 보였는지 한 줄만 알려 주세요
```
사실 줄은 그대로 써도 되지만, ⚠ 줄은 수강생이 "맞다"고 하기 전에는 겪은 일로 쓰지 않습니다. 확인하지 못하면 4-3으로 넣습니다.

### 4-3. 코드만 보고 한 추측 (비교로 쓰기)
기능의 **의도**(문서가 밝힌 목표·목표한 경험)와 **지금 코드의 동작**을 읽고, 그 코드가 무엇을 막고 있는지에서 거꾸로 추측합니다.
예: 역순 `for` → 순회 중 제거 오류 / `destroyCancellationToken` → 파괴 뒤 콜백 / `HashSet` → 중복 판정 / `Time.deltaTime` 곱 → 프레임 의존 / 캐싱 → 매 프레임 `GetComponent`·`Find`.

후보를 1~2개 보여 주고, 문서에 넣는 방식은 **두 가지 중에서 고르게** 합니다.
- **겪은 일로 쓰기** — 수강생이 "그랬던 것 같다, 맞다"고 확인한 경우만.
- **비교로 쓰기** — 확인하지 못한 경우. "처음 떠올릴 법한 방식(…)으로 짜면 …(문제)가 생기기 때문에 지금은 …(바꾼 방식)으로 짰다"처럼, 겪은 일이 아니라 **지금 코드가 왜 이 모양인지**를 설명합니다.
  문제는 지금 코드로 확인할 수 있는 것만 씁니다(재현 방법이나 코드 줄을 함께). 이것도 4 · 고민과 선택이 아니라 과정 설명으로 인정됩니다.

```markdown
(형식 예시 — 실제 프로젝트와 무관)
**§3.4 데이터 테이블** — 코드만 보고 한 추측(커밋 기록 없음)
- 지금 코드: `DataManager.Load()`가 TSV를 읽어 `Dictionary<int, AnimalDef>`로 둠(§3.4 코드 블록)
- ⚠ 추측: 수치를 스크립트나 ScriptableObject에 두면 18종을 고칠 때마다 에셋을 하나씩 열어야 했을 것
- 겪은 일로 쓰기 — 실제로 그랬다면: 처음(…) → 문제(…) → 바꾼 방식(TSV 한 파일)
- 비교로 쓰기 — 기억나지 않으면: "동물마다 에셋을 두면 …라서, 지금은 …"
- 고를 것: 겪은 일 / 비교 / 넣지 않음
```

- 추측할 근거가 코드에 없으면 "근거가 부족해 추천하지 않습니다"라고 쓰고, 그 기능에서 겪은 다른 문제를 문제 → 원인 → 해결로 적는 길을 안내합니다.
- 추천 문장은 **초안**입니다. 수강생이 자기 말로 고쳐 쓰도록 권합니다(가이드 원칙: *"내가 만든 것을 설명할 줄 안다"*).

## 5. 문서에 넣기 (수강생이 고른 것만)

1. 기능마다 수강생의 선택(겪은 일 / 비교 / 넣지 않음)과 최종 문장을 받습니다. 수강생이 문장을 고쳐 주면 그 문장을 그대로 씁니다.
2. 넣을 자리는 **그 기능의 절 안**입니다. 문서에 이미 과정 틀이 있으면(예: "지금 다시 보면 → 바꾼 것", "지금 모습이 되기까지" 표, "문제 → 원인 → 해결") 그 틀을 그대로 따르고, 없으면 지금 코드 블록 바로 앞에 짧은 문단 하나로 넣습니다.
   새 절 제목을 만들지 않습니다. 꼭 필요하면 "번호 + 이름"만(대시 뒤 요약 없이).

## 6. 페이지에 반영 (자동 빌드)
